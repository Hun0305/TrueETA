# 운영계정 신청 (활용사례 등록)

공공데이터포털에서 개발계정(1,000건/일) → 운영계정으로 올리기 위한 제출 자료.
**폼에 그대로 복붙할 수 있게** 정리했다.

> 아직 급하지 않다. 현재 사용량이 700콜/일이라 한도 안이다.
> 정류장을 3곳 이상 담거나 남에게 공개할 때 필요해진다.

---

## 1. 조건은 하나 — 활용사례 등록

"운영계정으로 바꿔주세요" 가 아니라 **"이걸 만들었습니다" 를 증명**하는 절차다.
서비스 설명 + 화면 캡처를 등록하면 된다.

우리가 쓰는 API 는 심의가 **자동승인**이라 담당자 반려 위험이 낮다.
(일반적으로는 담당자가 2~3일 검토하고 내용이 부실하면 반려된다.)

| API | 개발계정 | 운영계정 | 심의 |
|---|---|---|---|
| [경기도_버스도착정보 조회](https://www.data.go.kr/data/15080346/openapi.do) | 1,000/일 | 활용사례 등록 시 증가 가능 | **자동승인** |
| 경기도_버스노선 조회 | 1,000/일 | 확인 필요 | 확인 필요 |
| 경기도_정류소 조회 | 1,000/일 | 확인 필요 | 확인 필요 |

**세 API 를 각각 신청해야 한다.** 도착정보만 확인했고 나머지 둘은
각자 페이지의 "신청 가능 트래픽" 과 "심의여부" 를 봐야 한다.

---

## 2. 신청 절차

1. 공공데이터포털 로그인 → **마이페이지 → 오픈API → 활용신청 현황**
2. 해당 API 의 `[승인] …` 항목을 열어 **운영계정 신청**
3. 활용사례 등록 폼에 아래 3장 내용을 붙여넣는다
4. 화면 캡처 첨부 (4장)
5. 일일 트래픽에 **10,000** 입력 (5장 근거)

---

## 3. 폼에 붙여넣을 내용

### 활용사례명

```
회차대기를 구분해 보여주는 버스 도착 전광판
```

### 서비스 개요

```
라즈베리파이와 8인치 LCD로 만든 개인용 버스 도착정보 상시 표시 장치입니다.
집 앞 정류장 2곳에 정차하는 마을버스 22·25·59번의 도착정보를 노선당 다음
2대까지 한 화면에 띄웁니다.

[만들게 된 이유]
기존 지도 앱은 노선마다 정류장이 달라 여러 번 조회해야 하고, 무엇보다
회차지에서 출발을 기다리는 차량의 예상시간이 실제 도착시간처럼 보입니다.
"4분 뒤 도착"을 보고 나갔다가 15분을 기다린 적이 있습니다.

predictTime은 "지금 위치에서 여기까지 달리면 4분"이라는 뜻이지, 회차지에서
얼마나 더 서 있을지를 포함하지 않기 때문입니다. 특히 25번은 회차점이
정류장에서 4정거장밖에 떨어져 있지 않아 이 착각이 자주 일어납니다.

[핵심 기능 — 회차대기 판정]
API가 제공하는 필드를 조합해 "지금 움직이고 있는 차"와 "회차지에 서 있는 차"를
구분해 표시합니다.

1. flag = WAIT (회차지대기)  : API가 확정해준 경우
2. 차량 위치 순번            : staOrder - locationNo 가 기점(1)이나
                               turnSeq(회차점)와 같으면 대기 지점에 있는 것으로 봅니다.
                               조회 1회로 판정되므로 즉시 표시할 수 있습니다.
3. ETA 감소율                : (이전 예상시간 - 현재 예상시간) / 경과 시간.
                               정상 주행은 0.6~1.0, 회차대기는 0에 가깝습니다.
                               시내·마을버스는 정시 시간표가 없어 배차간격만
                               제공되므로, 시간표 대조 대신 이 값을 기준선으로 씁니다.

회차지에 있는 차량은 예상시간을 회색으로 표시하고 "회차지 · 더 걸릴 수 있음"
문구를 함께 띄웁니다. 숫자를 지우지 않는 것은 "빨라야 5분"이라는 정보가
"언제 올지 모름"보다 판단에 쓸모 있기 때문입니다.

[사용 방식]
- 조회 대상: 정류소 2곳, 노선 3개
- 조회 주기: 운행시간(05:50~00:10) 안에서만 조회하며, 실제로 버스를 타는
  08:00~18:00은 2분, 그 외 시간대는 10분 주기입니다.
  첫차 전·막차 후에는 호출하지 않습니다.
- 화면은 마지막 조회 시각을 기준으로 남은 시간을 1초씩 줄여 표시하므로,
  조회 주기가 길어도 호출을 늘리지 않고 부드럽게 보여줍니다.
- 조회한 데이터는 장치 내부에서만 사용하며 외부 공개·제3자 제공·재배포를
  하지 않습니다.

[사용 API 및 필드]
- 버스도착정보 조회(getBusArrivalListv2)
  flag, staOrder, turnSeq, locationNo, stateCd, predictTime(Sec),
  vehId, plateNo, routeId, routeName, routeDestName
- 버스노선 조회(getBusRouteInfoItemv2, getBusRouteStationListv2)
  첫차·막차, 배차간격, 회차정류소, 경유 정류소 순번
- 정류소 조회(getBusStationListv2, getBusStationAroundListv2,
  getBusStationViaRouteListv2)
  정류장 검색과 경유 노선 확인. 정류장 하나에 양방향 두 개가 있고 이름이
  같아서, 노선의 진행방향 종점(routeDestName)을 함께 보여줘 사용자가
  방향을 잘못 고르지 않도록 했습니다.

[개발 환경]
Python(FastAPI), SQLite, 라즈베리파이 4B, Raspberry Pi OS
소스 공개: https://github.com/Hun0305/TrueETA
```

| 파일 | 내용 |

| [screenshots/edit.png](screenshots/edit.png) | 프리셋 편집 — 양방향 구분과 방면 표시 |

**`board-real.png` 를 권한다.** 회차지 경고가 이 서비스의 존재 이유이고,
실제 정류장 이름이 있어야 동작하는 서비스로 보인다.

거주지 노출이 걸리면 `board-neutral.png` 를 쓴다. 단 활용사례는 포털에
공개되므로, 저장소를 이미 공개해둔 이상 실익은 크지 않다.

### 다시 찍는 방법

화면 상태를 바꿔 찍고 싶으면 데모 모드를 쓴다. **API 를 타지 않아 쿼터가 들지 않는다.**

```bash
.venv/bin/python -m trueeta                      # 서버 띄우고
# 브라우저에서 http://localhost:8099/?demo=1
```

데모 데이터는 [web/index.html](../src/trueeta/web/index.html) 의 `DEMO_BOARD`
에 있고, 회차대기 표시 세 가지(정상 / 확정 배지 / 회차지 경고)가 다 나오게
짜여 있다.

명령줄에서 바로 PNG 로 뽑으려면:

```bash
MOZ_HEADLESS=1 firefox --headless \
  --screenshot "$(pwd)/docs/screenshots/board.png" \
  --window-size=1024,768 "http://localhost:8099/?demo=1"
```

> `--screenshot` 의 경로는 **절대경로**여야 한다. 상대경로를 주면
> 조용히 아무것도 안 만든다.
>
> Chromium 헤드리스는 이 라즈베리파이에서 멈춰서 Firefox 를 쓴다.
> 다만 Firefox 는 `fetch` 완료를 기다리지 않고 캡처하므로, 서버에서
> 받아온 실데이터를 찍으려면 화면이 뜬 뒤 수동으로 찍는 편이 확실하다.
> 위 명령은 `?demo=1`(동기 렌더링)이라 문제없다.

## 5. 요청할 일일 트래픽 — 10,000

현재 사용량과 확장 여지를 계산한 값이다.

| 상황 | 주기 | 하루 호출 |
|---|---|---|
| 현재 (개발계정) | 피크 120초 / 그 외 600초 | **700** |
| 운영계정 후, 정류장 2곳 | 피크 60초 / 그 외 300초 | 1,400 |
| 정류장 3곳 | 〃 | 2,100 |
| 정류장 5곳 | 〃 | 3,500 |
| 정류장 8곳 | 〃 | 5,600 |

여기에 프리셋 편집의 정류장 검색(약 100콜/일)과 개발·테스트 여유(약 200콜/일)를
더하면 **10,000건이면 충분하고, 과하지도 않다.**

신청 사유로 쓸 문구:

```
현재 개발계정(1,000건/일)으로는 정류장 2곳을 피크 시간대 2분 주기로 조회하는
것이 한계입니다(하루 700건). 조회 주기를 1분으로 줄이고 정류장을 5곳까지
늘리면 약 3,500건이 필요하며, 정류장 검색과 개발·테스트 여유를 포함해
10,000건을 신청합니다.

호출량을 줄이기 위해 이미 아래를 적용하고 있습니다.
- 운행시간(05:50~00:10) 밖에는 호출하지 않음
- 실제 이용 시간대(08:00~18:00)만 짧은 주기, 나머지는 10분 주기
- 화면에 표시 중인 정류장만 조회 (보지 않는 설정은 호출하지 않음)
- 같은 정류장을 여러 화면이 공유하면 조회는 1회만
- 정류장 검색 결과는 30분간 캐시
```

## 6. 신청 후

- 반영까지 시간이 걸릴 수 있다. `.env` 의 서비스키는 **그대로**다
  (계정 등급만 바뀌고 키는 같다)
- 트래픽이 늘면 [config.yaml](../config.yaml) 의 `polling.daily_budget` 을
  올리고 `interval_sec.peak` 를 60 으로 내린다.
  주기는 `daily_budget` 에서 역산되므로 예산만 고쳐도 자동으로 조정된다
- `var/quota.json` 의 카운터는 세기만 하고 막지 않는다.
  한도를 넘기면 GBIS 가 거절해 그날 남은 시간 내내 화면이 에러가 되므로,
  주기를 바꾼 뒤에는 `test_daily_calls_stay_under_the_dev_quota` 를 확인할 것
