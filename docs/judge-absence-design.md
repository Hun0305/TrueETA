# 회차대기 판정 B안 — "차 없음"을 읽는다

현재 판정(A안, [judge-algorithm.md](judge-algorithm.md))의 전제가 실측으로 깨졌다.
이 문서는 대안(B안)과, **두 안을 동시에 기록해 비교하는 방법**을 정리한다.

상태: **설계만.** 구현 전이다. (2026-09-29)

---

## 1. 발견 — 회차지에 서 있는 차는 API 에 안 나온다

9/24·9/28 관측 374행, 세 노선의 1·2호차 전부에서 **회차점·기점 위치의 차가 한 번도
잡히지 않았다.** 셋 다 정확히 그 바로 다음 정거장까지만 보인다.

| 노선 | 회차점(기점) 위치 | 관측된 위치 범위 | 표본 |
|---|---|---|---|
| 22 | 회차점 11정거장 전 | 1 ~ **10** | 61 |
| 25 | 회차점 4정거장 전 | 1 ~ **3** | 44 |
| 59 (1호차) | 기점 21정거장 전 | 1 ~ **20** | 160 |
| 59 (2호차) | 〃 | 6 ~ **20** | 109 |

**GBIS 는 회차지를 출발한 차만 도착정보에 넣는다**고 보는 게 맞다.

그래서:

- A안의 위치 규칙 `staOrder − locationNo ∈ {1, turnSeq}` 은 **이 정류장들에서 발동할 수 없다.**
  실제로 374행 판정이 전부 `running` 이었다
- **회차대기의 실제 모습은 "차 없음"이다.** 9/28 운행시간 중 25번은 사이클의 71%,
  22번은 61% 가 차 없음이었다. 화면에는 회색 `—` 로 나왔다
- 처음 todo 에 적은 관찰 — *"회차지연 대기로 정보가 없으면 아예 회색으로 뜸"* — 이
  정확했다. A안은 이걸 "4분으로 떠서 속는다" 는 다른 문제로 잘못 풀었다

> 하루 반 치 데이터다. 패턴이 매우 깔끔하긴 하지만(세 노선 모두 경계 −1 에서 끊김)
> 며칠 더 쌓아 확인해야 한다. 그래서 B안을 바로 교체하지 않고 **나란히 기록**한다 (4장).

---

## 2. B안 — 운행 중 "차 없음"은 "아직 회차지를 안 떠났다"

타는 사람 입장에서 **회차지 대기와 배차 공백은 같은 것이다** — 둘 다 "다음 차가 아직
출발 안 했다" 이다. 그러니 B안은 둘을 구분하려 하지 않는다.

```
운행시간 안 + 도착정보에 이 노선 차가 없음
  → 상태 UNSEEN ("회차지 대기")
  → 최소 N분 · 예상 M분 을 함께 보여준다
```

운행시간 밖(첫차 전·막차 후)의 "차 없음"과는 구분해야 한다. 지금은 `service_window`
하나로 뭉뚱그리는데, 노선마다 첫차·막차가 다르므로 **노선별 운행시간**이 필요하다 (3장).

---

## 3. N 과 M 을 어디서 얻나

### 최소 N — 회차점에서 우리 정류장까지 주행시간 (로그에서 학습)

차가 회차점을 막 떠나 처음 잡힐 때의 ETA 가 곧 "출발하면 최소 이만큼 걸린다" 이다.

| 노선 | 처음 잡힐 때 위치 | 그때 ETA | **N** |
|---|---|---|---|
| 25 | 3정거장 전 | 157~190초 | **약 3분** |
| 22 | 10정거장 전 | 424~448초 | **약 7분** |

관측 로그에 이미 들어 있는 값이라 **노선별 중앙값을 주기적으로 다시 계산**하면 된다.
표본이 없는 노선은 설정의 기본값(예: 정거장당 60초)으로 시작한다.

### 예상 M — 배차간격 (버스노선 API)

마지막 차가 우리 정류장을 지나간(또는 목록에서 사라진) 시각을 `t_last`,
배차간격을 `H` 라 하면

```
M = max(N,  t_last + H − 지금)
```

"보통은 이쯤 온다" 는 값이다. 틀릴 수 있어서 화면에서 **추정**임을 드러낸다.

`H` 는 [버스노선 조회](https://www.data.go.kr/data/15080662/openapi.do) 의
`peekAlloc`(평일 피크)·`nPeekAlloc`(비피크)·`sat*`·`sun*` 에서 온다.

| 노선 | 피크 | 비피크 | 첫차~막차(평일, 우리 방향) |
|---|---|---|---|
| 22 | 15분 | 25분 | 06:00~23:55 |
| 25 | 15분 | 20분 | 06:30~23:45 |
| 59 | 14분 | 15분 | 06:30~23:30 |

실측 "차 없음" 구간이 대부분 이 범위에 들어온다 — 25번 8~20분(가끔 40분),
22번 6~30분. **40분짜리가 원래 겪은 "15분 기다림" 같은 경우**일 가능성이 있다.

`route-info` 는 **하루 1회** 받아 캐시한다. 노선 3개 = 하루 3콜이고,
도착정보와 **다른 오퍼레이션이라 쿼터 주머니가 따로**다. 지금 런타임에서 안 쓰던
버스노선 API 를 이제 쓰게 된다 (운영계정 신청 대상은 여전히 도착정보뿐).

같은 응답의 첫차·막차로 노선별 운행시간도 정한다 → 2장의 "운행 밖 차 없음"과 구분.

## 4. 두 안을 동시에 기록하기 (그림자 운영)

**추가 API 호출 없이 된다.** 같은 도착정보 응답을 A·B 두 방식으로 판정하고 둘 다 남긴다.

### 새 테이블이 필요한 이유

지금 `observations` 는 **차가 있을 때만** 행을 남긴다. B안의 핵심은 차가 **없는**
순간이라, 지금 로그로는 B안을 평가할 수 없다. 사이클마다 (정류장, 노선) 한 줄씩,
차가 있든 없든 남기는 표를 추가한다.

```sql
CREATE TABLE route_cycles (
    ts             TEXT NOT NULL,     -- 사이클 시각
    station_id     TEXT NOT NULL,
    route_name     TEXT NOT NULL,
    n_vehicles     INTEGER NOT NULL,  -- 0 이면 '차 없음'
    eta1_sec       INTEGER,           -- 1호차 ETA (있을 때)
    loc1           INTEGER,
    in_service     INTEGER,           -- 노선별 첫차~막차 안인가
    absent_since   TEXT,              -- 차 없음이 시작된 시각 (연속 구간 추적)
    a_status       TEXT,              -- A안 판정
    b_status       TEXT,              -- B안 판정 (RUNNING / UNSEEN / OFF)
    b_min_sec      INTEGER,           -- B안이 낸 N
    b_expected_sec INTEGER,           -- B안이 낸 M
    PRIMARY KEY (ts, station_id, route_name)
);
```

기존 `observations`(차량 단위)는 그대로 둔다. A안 튜닝(감소율)에 계속 쓴다.

용량: 사이클당 3줄 × 하루 약 350사이클 ≈ 하루 1,000줄. 문제없다.

### 나중에 이걸로 답할 것

- B안이 `UNSEEN, 예상 12분` 이라 했을 때 **실제로 차가 몇 분 뒤 도착했나** → M 의 오차
- 차가 처음 나타난 순간의 ETA 분포 → N 을 노선별로 다시 학습
- A안이 `WAITING` 을 한 번이라도 낸 적이 있나 → 없으면 A안 위치 규칙은 삭제 후보
- `absent_since` 로 "차 없음" 구간 길이 분포 → 배차간격 H 가 실제와 맞나

[scripts/analyze.py](../scripts/analyze.py) 에 `--compare` 로 붙인다.

## 5. 화면

지금 `—` 로 나오는 칸이 바뀐다.

| 상황 | 지금 (A안) | B안 |
|---|---|---|
| 차가 오는 중 | `4분` | `4분` (같음) |
| 운행 중인데 차 없음 | `—` 회색 | **`회차지 대기`** + `최소 3분 · 보통 ~12분` |
| 첫차 전·막차 후 | `—` 또는 `운행종료` | `운행종료` / `첫차 06:30` |

"최소 3분" 이 핵심이다. 차가 안 보이는 25번을 보고 **최소 3분은 여유가 있다**는 걸
알 수 있다. 반대로 원래 문제처럼 "금방 오겠지" 하고 나가는 걸 막으려면 `보통 ~12분` 을
같이 보여줘야 한다.

그림자 기간 동안 무엇을 화면에 보여줄지는 설정으로 고른다.

```yaml
judge:
  display: b     # a | b   — 기록은 항상 둘 다
```

A안의 화면 결과는 이 정류장들에서 사실상 `—` 뿐이라, **B안을 보여줘도 잃는 게 없다.**
다만 B안은 검증 전이므로 `보통 ~12분` 에는 `~` 와 흐린 색으로 추정임을 드러낸다.

## 6. 한계

- **veh_id 가 재사용된다.** 같은 차가 하루에 여러 번 왕복하므로 "차량별 첫 등장" 으로는
  첫 운행만 잡힌다. N 학습은 **"차 없음 → 차 있음" 전환 시점**의 ETA 로 해야 한다
- **사이클 간격만큼 뭉개진다.** 피크 2분·비피크 10분이라 "차 없음" 구간 길이가
  그 단위로 끊긴다. 운영계정으로 1분 주기가 되면 정밀해진다
- **배차간격은 계획값이다.** 실제는 더 들쭉날쭉하다(25번 40분 공백). M 은 틀릴 수 있다
- **회차지를 떠났는데 목록에 늦게 뜨는 경우**는 구분 못 한다. GBIS 반영 지연이 있다면
  N 이 실제보다 작게 학습된다
- 2호차도 같은 이유로 회차지 대기 중이면 안 보인다. "1대만 보임"도 정보다

## 7. 구현 순서

1. **`route_cycles` 기록부터** — 판정 없이 `n_vehicles`·`eta1`·`loc1` 만 남겨도 B안 평가
   데이터가 쌓이기 시작한다. **하루 늦을수록 하루치 비교 데이터를 잃는다**
2. `route-info` 하루 1회 캐시 (노선별 첫차·막차·배차간격)
3. B안 판정 함수 — 순수 함수, A안(`judge.py`)과 나란히
4. 두 판정을 `route_cycles` 에 같이 기록
5. 화면에 `judge.display` 반영
6. `analyze.py --compare`

1번은 판정·화면을 안 건드리므로 A안 관측 데이터의 연속성도 깨지 않는다.
