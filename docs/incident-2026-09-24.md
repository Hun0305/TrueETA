## 1. 원인 A — 테스트가 실제 프리셋 DB 를 덮어썼다 (주원인)

### 무슨 일이

`tests/test_api.py` 의 픽스처가 이랬다.

```python
monkeypatch.setattr(api_mod, "_store", store)      # 임시 DB 로 바꿔치기
monkeypatch.setattr(api_mod, "_search", FakeSearch())
with TestClient(api_mod.app, raise_server_exceptions=False) as _:   # ← 문제
    pass
return TestClient(api_mod.app)
```

`with TestClient(...)` 는 **lifespan 을 실행한다.** lifespan 안에서
`_store = PresetStore(settings.presets_path)` 가 돌면서 방금 바꿔치기한
임시 DB 를 **실제 `var/presets.db` 로 되돌렸다.**

그 뒤 테스트들이 실제 DB 에 썼다:

| 프리셋 | 테스트가 쓴 값 | 정상값 |
|---|---|---|
| 집앞 | `S3` / `y` / 노선 7 | 도담마을 22·59 + 대일초교 25 |
| **출근 (기본으로 지정됨)** | `S4` / `z` / 노선 9 | 존재하지 않음 |
| 출근2 | `S5` / `w` / 노선 3 | 존재하지 않음 |

`test_changing_default` 가 `출근` 을 **기본 프리셋으로 바꿔놓기까지 했다.**
기본 프리셋은 키오스크가 상시 띄우고 항상 폴링되는 것이다.

### 왜 이틀이나 몰랐나

**조용히 실패했기 때문이다.** 세 가지가 겹쳤다.

1. **존재하지 않는 `stationId` 와 "지금 오는 차 없음" 이 구분되지 않는다.**
   GBIS 는 `S4` 조회에 `resultCode=4`(결과 없음)를 준다. 우리 코드는 이걸
   **정상**으로 취급한다 — 막차 후에는 당연히 결과가 없기 때문이다.
   그래서 에러 로그가 한 줄도 안 남았다.

2. **사이클 로그를 내가 지웠다.** 프리셋 리팩터링 때 `보드 갱신: N줄`
   로그를 빼버려서, 폴러가 매 사이클 뭘 하는지 볼 수 없었다.

3. **픽스처를 고쳤지만 피해를 확인하지 않았다.** 테스트가 실패하는 걸 보고
   픽스처는 바로 고쳤는데, *이미 망가뜨린 실제 DB* 는 들여다보지 않았다.

### 조사 중 내가 또 틀린 것

처음엔 `journalctl --list-boots` 가 부팅 1개만 보여줘서
**"어제 라즈베리파이가 안 켜져 있었다"** 고 단정했다. 틀렸다.

`var/quota.json` 에 `"2026-09-23": {"arrivals": 174}` 가 남아 있었다.
기계는 돌았고 폴러도 174번 호출했다. 저널이 29.5MB → 8MB 로 줄면서
이전 부팅 기록이 날아간 것을 **한 소스만 보고** 기계 상태로 결론냈다.

> 교훈: 로그가 비었다는 것은 "일이 안 일어났다" 가 아니라
> "그 로그에 안 남았다" 는 뜻이다. `quota.json` 처럼 다른 경로로 남는
> 흔적을 먼저 대조할 것.

## 2. 원인 B — 라즈베리파이에 RTC 가 없다 (부차)

### 무슨 일이

```
2026-09-24T01:00:17  Started trueeta.service
2026-09-24T01:00:21  운행시간 밖 (05:50~00:10) — 조회 중지
2026-09-24T20:42:31  운행시간 진입 — 조회 재개
```

실제 부팅은 **20:41** 이었다. 라즈베리파이에는 RTC 가 없어서 전원을 끊으면
시계가 멈추고, 부팅 직후에는 엉뚱한 시각(여기서는 01:00)으로 시작한다.
`fake-hwclock` 도 설치돼 있지 않아 마지막 시각 복원조차 안 된다.

폴러는 그 시각을 믿고 **"지금 01시, 운행시간 밖이니 자자"** 하고 잠들었다.
NTP 가 20:42 에 고쳐준 뒤에야 깨어났다.

이번에는 90초만 잃었지만, **네트워크가 늦게 붙으면 그만큼 통째로 건너뛴다.**
아침에 전원을 켰는데 시계가 새벽으로 잡히면 출근 시간 화면이 비어 있게 된다.

### 시계가 틀리면 같이 틀어지는 것

- **운행시간 판정** → 조회를 건너뛴다 (이번에 물린 것)
- **관측 로그의 `ts`** → 분석에서 경과 시간이 엉켜 감소율이 무의미해진다
- **`quota.json` 의 날짜** → 엉뚱한 날에 기록돼 한도 계산이 어긋난다

## 3. 행동

### 즉시 — 프리셋 복구

파일을 지우지 않고 **앱 자체 API 로** 정상값을 덮어썼다.

```python
for preset in cfg.presets:      # config.yaml 의 정상값으로 교체
    store.save(preset)
store.set_default(cfg.default_preset.name)
for p in store.all():           # 테스트가 만든 가짜 프리셋 제거
    if p.name not in {x.name for x in cfg.presets}:
        store.delete(p.name)
```

`출근`·`출근2` 를 제거하고 `집앞` 을 기본으로 되돌렸다.
`config.yaml` 이 씨앗으로 남아 있어 복구가 가능했다 — 이 설계가
여기서 값을 했다.

### 시계 — 동기화를 기다린 뒤 폴링 시작

[src/trueeta/clock.py](../src/trueeta/clock.py) 를 추가했다.

```python
if not await wait_for_sync():
    log.warning("시계 동기화를 확인하지 못했다 — 현재 시각을 그대로 믿고 진행한다")
```

`systemd-timesyncd` 가 동기화에 성공하면 만드는
`/run/systemd/timesync/synchronized` 를 본다.

**무한정 기다리지 않는다.** 기본 120초에서 포기하고 경고만 남긴 뒤 진행한다.
네트워크가 영영 안 붙는 상황에서 화면이 영원히 비는 것보다,
틀릴 수 있는 시계로라도 도는 편이 낫다.

유닛 파일에도 방어선을 하나 더 뒀다
([scripts/trueeta.service](../scripts/trueeta.service)).

```ini
After=network-online.target time-sync.target
Wants=network-online.target time-sync.target
```

> `time-sync.target` 이 실제로 '동기화 완료' 를 뜻하려면
> `systemd-time-wait-sync` 가 켜져 있어야 한다. 이 기기는 꺼져 있다:
> ```bash
> sudo systemctl enable --now systemd-time-wait-sync
> ```

      에 유닛 변경 반영 (sudo 필요)
- [x] **저널이 재부팅마다 사라지는 문제** (2026-09-29)

      남기게 했다 ([logging.md](logging.md))
