# 즐겨찾기(프리셋) 설계

고정된 22·25·59 대신 **본인이 정류장·노선을 골라 묶음으로 저장하고,
그중 하나를 골라 띄우는** 형태로 바꾸는 계획.

아직 구현되지 않았다. 설계와 단계만 정리한 문서다.
현재 구조는 [architecture.md](architecture.md), 판정은 [judge-algorithm.md](judge-algorithm.md).

---

## 1. 무엇을 만들려는가

지금은 `config.yaml` 에 박힌 정류장 2곳만 본다.

원하는 것:

- 정류장과 노선을 직접 골라 **묶음(프리셋)** 으로 저장
- 묶음을 여러 개 만들어 두고 필요한 것 하나를 띄운다
- 예: "집앞"(22·59·25) / "출근-신분당"(죽전 59 vs 미금 22·25 비교)

마지막 예가 이 기능이 필요한 진짜 이유다.
**신분당선을 타러 갈 때 죽전에서 59를 탈지, 미금까지 가서 22·25를 기다릴지**는
서로 다른 정류장 여럿을 한 화면에서 비교해야 판단할 수 있다.

---

## 2. 이미 가진 것

정류소 조회 서비스를 1차 때 신청해뒀고 [operations.py](../src/trueeta/gbis/operations.py)
에 등록돼 있다. **추가 활용신청 없이 바로 쓸 수 있다.**

| 오퍼레이션 | 프리셋 편집에서의 쓰임 |
|---|---|
| `station-list --keyword` | 정류장 이름·번호로 검색 |
| `station-around --x --y` | 좌표 반경 500m — 폰 GPS 로 "내 주변" |
| `station-routes --station` | 그 정류장을 지나는 노선 목록 (체크박스 채우기) |
| `station-info --station` | 정류장 상세 |

화면·판정·저장(SQLite) 코드도 이미 있다.
**새로 필요한 건 UI 와 폴링 모델 변경뿐이다.**

---

## 3. 진짜 제약 — 쿼터가 아키텍처를 바꾼다

개발계정 한도는 **1,000건/일**. 1사이클에 정류장 1곳당 1콜이다.

지금은 `config.yaml` 에 고정된 2곳을 **항상** 폴링한다.
프리셋이 3개고 각각 정류장 3곳이면 9곳 — 전부 돌리면 하루 3,150콜로 한도의 3배다.

### 전환: "고정된 곳을 항상" → "지금 보고 있는 것만"

| | 폴링 |
|---|---|
| 키오스크가 상시 띄운 프리셋 | 계속 |
| 폰에서 열어둔 프리셋 | **열려 있는 동안만** |
| 안 보는 프리셋 | **0콜** |

프리셋을 여러 개 저장해도 **동시에 활성인 것만** 비용이 든다.
저장 개수는 공짜고, 화면에 띄우는 개수가 비용이다.

### 주기는 활성 정류장 수에서 역산한다

```
운행시간 = 66,000초 (05:50 ~ 00:10)
최소 주기 = 운행시간 × 활성 정류장 수 / 일일 예산
```

| 활성 정류장 | 최소 주기 |
|---|---|
| 1곳 | 66초 |
| 2곳 | 132초 |
| 3곳 | 198초 (3.3분) |
| 5곳 | 330초 (5.5분) |
| 8곳 | 528초 (8.8분) |

**지금은 주기가 상수라 이 계산이 없다.**
`interval_peak_sec = 120` 은 "정류장 2곳" 을 전제로 손으로 맞춘 값이다.
프리셋을 도입하면 정류장 수가 변하므로 **계산해서 정해야 한다.**

주기가 길어지면 화면 보간이 더 낙관적으로 어긋난다는 점도 같이 걸린다
([judge-algorithm.md 6장](judge-algorithm.md#6-eta-감소율--시간표를-대신하는-기준선)).
정류장을 많이 담은 프리셋은 정확도가 떨어진다는 걸 화면에 알려야 한다.

## 4. 반드시 피해야 할 함정 — 방향

**정류장 하나에 `stationId` 가 두 개다.** 양방향이 각각 다른 ID 를 갖는다.
잘못 고르면 반대편으로 가는 버스를 보게 된다.

1차 때 직접 겪었다:

| 정류장 | 상행 | 하행 |
|---|---|---|
| 도담마을아이파크.죽전휴먼빌 | `228001207` | `228001059` |
| 대일초교후문 | `228003550` | `228003549` |

이름이 완전히 같아서 검색 결과만으로는 구분이 안 된다.
`routeDestName`(진행방향 종점)을 봐야 갈린다.

> **검색 결과에 정류장 이름만 띄우면 안 된다.**
> "도담마을아이파크 — **미금역 방면** / **죽전역 방면**" 처럼
> 종점을 같이 보여줘야 고를 수 있다.

종점은 `station-routes` 응답의 `routeDestName` 으로 얻는다.
정류장을 고르는 단계가 아니라 **노선을 고르는 단계에서** 방향이 드러나므로,
UI 흐름을 "정류장 검색 → 노선 선택(방향 표시)" 순으로 두면 자연스럽게 해결된다.

## 5. 데이터 모델

현재 [Stop](../src/trueeta/config.py) 과 같은 모양을 프리셋 아래로 옮기는 것이다.

```sql
CREATE TABLE presets (
    id          INTEGER PRIMARY KEY,
    name        TEXT NOT NULL,       -- "집앞", "출근-신분당"
    sort_order  INTEGER DEFAULT 0,
    created_at  TEXT
);

CREATE TABLE preset_items (
    preset_id   INTEGER NOT NULL REFERENCES presets(id) ON DELETE CASCADE,
    station_id  TEXT NOT NULL,
    station_name TEXT NOT NULL,      -- 표시용. API 가 안 될 때도 목록은 보여야 한다
    route_name  TEXT NOT NULL,
    dest_name   TEXT,                -- 방향. 고를 때 본 값을 그대로 보관
    sort_order  INTEGER DEFAULT 0
);
```

`station_name` 과 `dest_name` 을 **복제해서 저장하는 것은 의도적이다.**
API 가 죽어도 프리셋 목록은 보여야 하고, 사용자가 고를 때 본 방향이
나중에 바뀌었는지도 비교할 수 있어야 한다.

저장은 [storage.py](../src/trueeta/storage.py) 의 SQLite 패턴을 그대로 쓴다.
다만 관측 로그와는 **다른 파일**로 둔다 — 관측 로그는 지워도 되는 데이터이고
프리셋은 아니다.

## 6. 바뀌어야 할 코드

| 파일 | 지금 | 바뀔 것 |
|---|---|---|
| [config.py](../src/trueeta/config.py) | `BoardConfig.stops` 고정 | 프리셋 저장소에서 읽는다. `config.yaml` 은 기본값·예산만 |
| [state.py](../src/trueeta/state.py) | `BoardState` 가 **보드 1개** | 프리셋별 보드. `dict[preset_id, Board]` |
| [poller.py](../src/trueeta/poller.py) | `config.stops` 를 항상 순회 | **활성 프리셋** 의 정류장만. 주기도 거기서 역산 |
| [api.py](../src/trueeta/api.py) | `GET /api/board` 하나 | `/api/board?preset=`, 프리셋 CRUD, 정류장 검색 프록시 |
| [web/index.html](../src/trueeta/web/index.html) | 보드 한 장 | 프리셋 선택 + 편집 화면 |

`StallTracker` 는 `(station_id, route_id, veh_id)` 로 키를 잡으므로
프리셋이 달라도 같은 정류장이면 이력이 공유된다. **그대로 두면 된다.**

## 7. 단계

### 1단계 — 프리셋을 `config.yaml` 에 여러 개 (하루)

DB·UI 없이 폴링 모델만 바꾼다. 본인 용도의 90% 가 여기서 해결된다.

```yaml
presets:
  - name: 집앞
    stops: [...]
  - name: 출근-신분당
    stops: [...]
```

- `/?preset=출근-신분당` 으로 고른다
- 정류장 ID 는 `probe.py station-list` 로 찾아 손으로 넣는다
- 폴러는 **활성 프리셋만** 돌린다
- 주기는 3장 공식으로 역산한다

**가장 어려운 부분(폴링 모델)을 가장 먼저 한다.** 여기가 막히면 나머지는 의미가 없다.

### 2단계 — 저장을 SQLite 로

키오스크와 폰이 같은 목록을 본다. 5장의 스키마.

### 3단계 — 검색·편집 화면

`station-list` / `station-around` / `station-routes` 를 붙인다.
**4장의 방향 표시가 여기서 핵심이다.**

검색 호출도 쿼터를 먹는다는 점에 주의. 타이핑마다 부르면 안 되고,
입력이 끝난 뒤(디바운스) 한 번만 불러야 한다.

### 4단계 — 남에게 공개 (선택)

**운영계정 트래픽 증가 신청이 필수다.**
웹에 배포하면 남이 쓰는 호출도 전부 내 1,000콜에서 나간다.
이게 확장안의 진짜 벽이다. 이용자 10명이면 개발계정으로는 며칠도 못 간다.

## 8. 열린 질문

- **폰에서 열어둔 프리셋의 "활성" 을 어떻게 끝내나?**
  브라우저를 닫아도 서버는 모른다. 하트비트(화면이 N초마다 `/api/board` 를
  부르는 것)가 끊기면 비활성으로 보는 방식이 단순하다.
  이미 화면이 15초마다 폴링하므로 그 신호를 쓰면 된다.
- **키오스크 프리셋을 어떻게 고정하나?** 설정 파일? URL? 둘 다?
- **정류장이 폐지되면?** 저장된 `station_id` 가 `resultCode=4` 를 돌려준다.
  프리셋에서 그 줄만 "확인 필요" 로 표시하고 나머지는 계속 보여줘야 한다.
- **프리셋마다 주기가 달라지면 화면의 보간 오차도 달라진다.**
  정류장을 많이 담을수록 부정확해진다는 걸 사용자가 알 수 있어야 하나?
